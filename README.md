# Dhaka Bus Network as a Graph — CSE173 project

This folder is the complete project from the plan: data, Python code, tests,
figures, a desktop app, a demo notebook and the proofs. This README is the step-by-step guide.
Follow the steps in order the first time; each step says **what to do**, **what
you should see**, and **why** it is done that way.

**Quick start (once Python and VS Code are installed):**

```bash
python -m venv .venv
.venv\Scripts\activate            # Windows   (macOS/Linux: source .venv/bin/activate)
pip install -r requirements.txt
pytest                            # 91 tests should pass
python run_all.py                 # sample, then Dhaka -> results/
python app.py                     # open the desktop app
```

## Step 4 — Run the tests first

```bash
pytest
```

You should see `91 passed`. In VS Code you can also open the **Testing** panel
(the flask icon) and click ▶.

What the tests check (`tests/`):

- On the sample, on Dhaka, and on 6 random graphs (some disconnected): our
  components, BFS hop counts, Dijkstra distances, cut vertices, bridges, MST
  weight and Warshall closure all equal NetworkX's answers.
- Known answers on the sample (for example: Technical → Sadarghat needs exactly
  2 bus changes, T2 → T1 → T3).
- Every validation rule catches the mistake it is meant to catch (a one-stop
  route, a stop twice in a row, a stop outside Dhaka, an unknown name, an alias
  used for two stops).
- Dijkstra refuses negative weights.
- The app's logic (`tests/test_gui_model.py`): route-finder answers, where to
  change buses, what closing a stop cuts off, and that the step-by-step Kruskal
  and Dijkstra states end in the same answers as the full algorithms.

*Why first:* if a test fails, the numbers in your report would be wrong. Running
tests before every analysis is the habit that makes your results defensible.

## Step 5 — Run the 11-stop sample and check it by hand

```bash
python run_all.py --data sample
```

(Or press **F5** / Run and Debug and pick **"Run sample only"**.)

The program prints the whole report and writes it to
`results/sample/summary.md`. Open it in VS Code with **Ctrl+Shift+V** (Markdown
preview).

### The sample network

Three made-up routes over 11 real stop names:

- **T1** (limited stop): Mirpur 1 → Mirpur 10 → Agargaon → Farmgate → Karwan Bazar → Shahbag
- **T2**: Mirpur 1 → Technical → Shyamoli → Asad Gate → Farmgate → Karwan Bazar
- **T3**: Shahbag → Gulistan → Sadarghat

It was designed so that every idea in the project shows up once:

| Result you should get | What it demonstrates |
|---|---|
| 11 vertices, 11 edges; sum of degrees 22 = 2·11 | handshaking theorem as a data check |
| Farmgate–Karwan Bazar is used by T1 and T2 but stored once | merging parallel routes |
| 1 component; Warshall closure is an equivalence relation | Chapters 9 and 10 linked |
| Cut vertices: Farmgate, Karwan Bazar, Shahbag, Gulistan; 4 bridges | resilience |
| Mirpur 1 → Farmgate: fewest stops = 3 hops, 7.69 km; shortest = 4 hops, 6.76 km | hops ≠ distance |
| Technical → Sadarghat: 2 bus changes (T2 → T1 → T3) | the route graph |
| MST = 10 edges, 17.66 km of 21.06 km; Mirpur 10–Agargaon (3.40 km) left out | Kruskal, cycle property |

### Hand checks to put in your report

1. **Weights.** Open `data/sample/processed/edges.csv`. Each `distance_km` is the
   haversine distance between the two stops' coordinates.
2. **Dijkstra by hand.** Using those weights, run Dijkstra from Mirpur 1 on
   paper. Compare with the table "Dijkstra step by step" in `summary.md`
   (also in `results/sample/dijkstra_trace.csv`).
3. **Kruskal by hand.** Sort the 11 edges by weight and add them one by one.
   Compare with "Kruskal step by step" (`kruskal_trace.csv`): only the 11th edge,
   Mirpur 10–Agargaon, is skipped because it would close the cycle.
4. **Cut vertices by hand.** Delete Farmgate from the drawing: the stops Karwan
   Bazar, Shahbag, Gulistan and Sadarghat are cut off.

*Why the sample first (plan, "Rules that save time"):* a bug in an 11-stop graph
can be traced by hand; the same bug in 100 stops cannot.

## Step 6 — How the code works, file by file

Read the files in this order. Every function has a docstring that explains it.

### 6.1 `src/data_prep.py` — cleaning and validation (Ch 1, Ch 2)

- **`normalise()`** trims spaces and ignores case, so `"  Farm  gate "` and
  `"Farmgate"` compare equal.
- **`build_alias_map()`** maps every spelling (official name + `aliases`) to one
  `stop_id`. If one spelling points to two stops, it stops with an error — the
  program cannot guess which you meant.
- **`clean()`** reads `route_stops_raw.csv` (names as you wrote them) and
  produces `processed/route_stops.csv` (stop IDs). Unknown names are listed all
  at once so you can fix them in one go. Raw files are never changed.
- **`validate()`** checks each rule as a proposition and lists counterexamples:

  | Rule | Proposition | If false |
  |---|---|---|
  | R1 | ∀ route r: r has ≥ 2 stops | stop |
  | R2 | ∀ (r, i, s): r ∈ Routes ∧ s ∈ Stops | stop |
  | R3 | ∀ r, i: sᵢ ≠ sᵢ₊₁ | stop |
  | R4 | ∀ r, i: d(sᵢ, sᵢ₊₁) ≤ 4 km | stop |
  | R5 | ∀ s: s inside the Dhaka box | stop |
  | R6 | ∀ r: seq numbers distinct | stop |
  | R7 | ∀ given road distance: road_km > 0 ∧ road_km ≥ haversine | stop |
  | W1 | ∀ r: no stop repeats (loop route) | warning only |
  | W2 | ∀ s: some route serves s (isolated vertex) | warning only |

  A counterexample is a witness for the negation ∃… ¬(…), which is how the
  program proves a rule false.

### 6.2 `src/graph_build.py` — the model (Ch 10.1–10.3, Ch 2)

- **Vertices** = stops (every stop, even one no route uses).
- **Edges** = pairs of consecutive stops on some route, `zip(seq, seq[1:])`.
- **Weight** w(e) = road distance from `road_km.csv` if you gave one, otherwise
  the haversine distance (which *underestimates* road distance — say so).
- **Labels** L(e) = the set of routes using the edge. Parallel routes on the same
  pair are merged into one edge, keeping the smallest weight, so the graph stays
  simple (Kruskal and Prim assume a simple graph).
- Stored as an **adjacency list** `adj[u][v] = km` (a dict of dicts): the graph is
  sparse, so this uses O(V + E) memory and BFS runs in O(V + E).
- **`handshake_check()`** compares the sum of degrees with 2|E|.
- **`route_graph()`** builds the second view: vertices are routes, and r₁, r₂ are
  linked when stops(r₁) ∩ stops(r₂) ≠ ∅ (a set intersection).

### 6.3 `src/algorithms.py` — the algorithms (Ch 10.4, 10.6, 11.4, 11.5, Ch 5)

| Function | Idea | Time |
|---|---|---|
| `bfs` | queue; first visit to v is along a fewest-hop path | O(V + E) |
| `connected_components` | BFS from each unvisited stop; one run = one component | O(V + E) |
| `dfs_recursive` | recursion: visit u, then recurse on each unvisited neighbour (Ch 5) | O(V + E) |
| `cut_vertices`, `bridges` | delete each vertex / edge and recount components | O(V(V + E)) |
| `dijkstra` | heap; move the closest outside stop into S, relax its edges | O((V + E) log V) |
| `dijkstra_trace` | same, but records each step for your hand trace | — |
| `fewest_bus_changes` | BFS on the route graph from all routes at the start stop | small |
| `kruskal` | sort edges, add unless union-find says it closes a cycle | O(E log E) |
| `prim` | grow from one stop by the cheapest leaving edge (restarts per component) | O(E log V) |
| `hop_summary`, `distance_summary` | BFS / Dijkstra from every stop: average, diameter, centre | V runs |

Neighbours are always visited in sorted order, so every run gives the same answer.

### 6.4 `src/relations_logic.py` — relations and logic (Ch 9, Ch 1)

- `adjacency_matrix()` and `warshall()` compute "can reach" as the
  reflexive-transitive closure of "directly linked".
- `is_reflexive / is_symmetric / is_transitive` prove the closure is an
  equivalence relation; `equivalence_classes()` returns its classes, which the
  report shows are exactly the BFS components.
- `connectivity_by_quantifiers()` evaluates ∀u ∀v path(u, v) directly and returns
  a witness pair for the negation if it is false.

### 6.5 `src/analysis.py` and `src/visualize.py`

`run_analysis()` calls everything above and writes `summary.md` (sections 1–10),
the CSV tables and the figures. `visualize.py` draws stops at their real
coordinates (longitude across, latitude up, corrected aspect ratio).

## Step 7 — The Dhaka data: what it is and how to improve it

**Read `data/dhaka/SOURCES.md` first.** In short: the 101 stop names are real,
the coordinates are approximate, and the 18 routes were built along real road
corridors but **have not been checked against real operator routes**. Every
route is marked `confidence = unverified`, and the summary prints a warning
about it. This is the plan's fallback option ("semi-synthetic data"); your job
before the final report is to verify as many routes as you can.

**Jinjira** is in `stops.csv` on purpose with no route serving it. It makes the
network disconnected (2 components), which demonstrates an isolated vertex and
the "true of the data, not necessarily of the city" point. Keep it and explain
it, or add a verified route to it.

### To fix or add a route

1. Edit `data/dhaka/raw/route_stops_raw.csv`: one row per stop, in order
   (`route_id, seq, stop_name`). Write names however you noted them.
2. If a name is new, add the stop to `raw/stops.csv` (new `stop_id`, name,
   `lat`, `lon` from Google Maps). If it is just another spelling, add it to that
   stop's `aliases`, separated by `|`.
3. Add or update the route's row in `raw/routes.csv` (`operator`, `source`,
   `confidence`).
4. Run `python run_all.py --data dhaka`. If a rule fails, the message names the
   route and position; fix the raw file and run again.

### To use real road distances (optional)

Add rows to `data/dhaka/raw/road_km.csv`: `stop_u, stop_v, distance_km, source`
(names or IDs). Those links then use your number; rule R7 checks that it is
positive and not shorter than the straight line.

### To choose the stop pairs for shortest paths

Edit `data/dhaka/pairs.csv` (`from_stop, to_stop`, names or IDs).

Open `results/dhaka/summary.md`. With the data as delivered you get:

| Section | Result (current data) | How to read it |
|---|---|---|
| 2. Size | 101 stops, 119 links; density 0.024; 58 links shared by several routes | very sparse; corridors are shared heavily |
| 3. Degrees | max 6 (Gulistan), mean 2.36; 8 end stops | most stops just pass traffic along a corridor |
| 4. Connectivity | 2 components: 100 stops + Jinjira; witness (Tongi, Jinjira) | the data, not the city, is disconnected |
| 5. Weak points | 23 cut vertices, 25 bridges; Gulistan cuts off 12 stops | the south-east (Jatrabari, Signboard) hangs on Gulistan–Tikatuli–Saidabad in this data |
| 6. Paths | e.g. Mirpur 12 → Motijheel: 13 hops / 15.38 km vs 15 hops / 13.42 km | fewest stops ≠ shortest distance |
| 7. Compactness | average 8.35 hops; diameter 25 hops (Tongi ↔ Signboard); 85% of pairs need ≤ 1 change | the route graph matters more to riders than hop counts |
| 8. MST | 99 edges, 90.83 km of 118.43 km (23% redundancy); cycle property holds | backbone, not a route proposal |
| 10. Cross-check | all "matches" | our algorithms agree with NetworkX |

These numbers will change as you correct the data — that is expected. Always
quote the numbers from your latest `summary.md`.

| File | Content |

| `degrees.csv` | every stop with degree and number of routes serving it |

| `map.html` | interactive map — double-click to open in a browser |

### How to talk about the results (for the discussion section)

- **Connectivity:** "In our data the network has 2 components. The second is
  Jinjira, for which we have no verified route; this is a gap in the data, not
  evidence that Jinjira has no buses."
- **Cut vertices:** a cut vertex in the data means "every route we recorded to
  that area passes through this stop". It is a candidate weak point to check,
  and the `confidence` column tells you how much to trust it.
- **Hops vs km:** a fewest-stop path can be several km longer (the summary lists
  the biggest differences), so "fewest stops" is a poor proxy for trip length.
- **Bus changes:** riders care about changes; the route graph shows most pairs
  need at most one change *in this data*.
- **MST:** the tree is the cheapest skeleton keeping every stop reachable; the
  left-out 23% of length is redundancy that gives riders shorter trips and
  alternatives when a road is blocked. Do not claim buses should follow it.

**Sidebar.** Switch between the **Sample** and **Dhaka** data sets (any extra

| Page | What you do | What it shows (course link) |
|---|---|---|
| **Overview** | look | Size cards (\|V\|, \|E\|, components, cut vertices, tree length), the network coloured by component with stop size = degree, busiest stops, average and longest trips, how many bus changes stop pairs need |

| **Spanning tree** | **Next ▶ / ◀ Back / Play**, or the keys **→ ←**, **space**, **Home / End**; click a row to jump | Kruskal's algorithm link by link: the tree so far (green), the link just added (orange), and for a skipped link the cycle it would close (purple) — the cycle property. At the end it compares with Prim |
| **Dijkstra steps** | choose the start stop, then step as above | The set S (blue, final), stops reached but not final (orange), the shortest-path tree, and which distances improved at each step. On the sample every stop shows its distance, so you can compare with your hand trace |
| **Data check** | **Reload data** after editing CSVs; **Run full analysis** writes everything to `results/` (same as `run_all.py`); open the results folder or `summary.md` | Each validation rule with ✓ / ! / ✗ and its counterexamples, the routes and their confidence, and the spellings the cleaner fixed. If the data has an error, the app opens here and shows it |

**How the app is built (for the report).** `src/gui/model.py` holds all the logic
and calls the same functions as the command-line pipeline (`data_prep`,
`graph_build`, `algorithms`), so the app and `run_all.py` always agree. It has no
GUI code, which is why it can be tested with pytest. The pages only ask it for
answers and draw them: Matplotlib draws the maps inside the window, and
CustomTkinter gives the modern buttons, cards and light/dark modes.

**For the presentation:** open the app on the Dhaka data, show the Overview, find
a route where the two paths differ (Mirpur 12 → Motijheel), close Gulistan on
Weak points, then press Play on Spanning tree. Use **Dark** if the projector
washes out light colours.

## Troubleshooting

| Problem | Fix |
|---|---|
| `python` not found | reinstall Python with "Add to PATH", or use `py` (Windows) / `python3` (macOS) |
| `No module named src` | run commands from the project folder (the one with `run_all.py`) |
| `No module named pandas` etc. | the venv is not active: activate it (Step 2) and `pip install -r requirements.txt` |

| `DATA PROBLEM: ... not in stops.csv` | add the stop, or add the spelling to `aliases` |
| `DATA PROBLEM: Validation failed: R4` | two consecutive stops are > 4 km apart: a stop is missing in between, or a coordinate is wrong. Raise the limit only if it is genuine: `--max-hop-km 5` |
| Notebook cannot find a kernel | Select Kernel → .venv; if missing, `pip install ipykernel` in the venv |
| Map is blank | `map.html` loads the map library and tiles from the internet; open it while online |
| App: `Tkinter is missing` | Windows/macOS: reinstall Python from python.org (Tkinter is included). Ubuntu: `sudo apt install python3-tk` |
| App: `CustomTkinter is not installed` | activate the venv and `pip install -r requirements.txt` |
| App window too big or text tiny | it sizes itself to the screen; drag the edge to resize. Windows display scaling (Settings → Display → Scale) also applies |
| App shows old data after editing CSVs | press **Reload data** on the Data check page |
| Bengali names look wrong | save CSVs as UTF-8 (VS Code: bottom bar → encoding → Save with Encoding → UTF-8) |
